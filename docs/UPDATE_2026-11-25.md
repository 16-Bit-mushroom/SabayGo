# System update, 25 Nov 2026

Branch `alpha-round2-prep`, in a pull request into `main`.

## In short

- **The Tapo door camera counted people and reported them to the server
  for the first time.** The whole path works: camera → phone → count →
  server, each count with its blurred photo, filed on the right trip in
  1–5 seconds. Accuracy is held back by camera placement, not software,
  as far as the tests can tell.
- **A new network no longer means a rebuild.** The console works on any
  network as built, and test phones get the laptop's address typed on
  the sign-in screen.
- **A deployment design is written** (`docs/DEPLOYMENT.md`): SabayGo on
  one cloud server at a fixed web address. It needs five decisions
  before it is built.

## 1. The Tapo door camera against the server

**Setup.** The Tapo C110 joins the realme's hotspot. The realme runs the
edge app (YOLOv8 on the phone) and reaches the laptop over its USB cable
(`usb_phones.sh --watch`). A test trip, "Tapo door test", was set up on
van TST-1023.

**Results.**

| Run | Camera | Walked | Counted |
|---|---|---|---|
| 1 | Doorway at the left edge of the picture | 3 in, 3 out | 2 in, 3 out |
| 2 | Re-aimed, line in the middle | 5 in, 5 out | 2 in, 5 out |

**What worked, every time.**
- The phone found the camera by itself, even though the hotspot changed
  its addresses after a restart.
- The door line drawn on the phone was saved on the server.
- Each count reached the server with its photo: the person is blurred,
  the line drawn in.
- Each count was filed on the right trip. There were no errors.

**Why entries were missed.** The phone keeps a frame-by-frame trace,
and it shows the same thing for every missed entry:
- The person is tracked from outside up to the line.
- There the model's confidence that it sees a person drops from about
  0.9 to 0.1–0.5, and the tracker loses them.
- They are picked up again only well inside, as a new person. Someone
  first seen inside is not counted as boarding, by design.

The camera was too close: a person filled 97 % of the picture's height,
with head and feet cut off, and crossed the whole picture in about 2
seconds. The phone analysed about 8 frames a second.

**Not settled yet.** Why exits held up better than entries, and whether
8 frames a second is enough once the camera is placed well. Both need a
run with the camera above a doorway, looking down, as in a van. If
entries are still missed then, the tracker is next. Today's trace lets
that be tested without walking again.

**Smaller findings.**
- The phone's "Inside now" figure stays one low after a missed entry.
  It is in minus out, never below 0. The server only stores it and
  decides nothing on it.
- The model once took hanging clothes for a person. They never moved,
  so they never crossed the line.

## 2. No rebuild when the network changes

| App | Before | Now |
|---|---|---|
| Console | the laptop's address was compiled in; a 3.5-minute rebuild at each new network | talks to the computer it was opened from; built once. Another computer on the same network opens `http://<laptop>:3001` |
| Passenger / Dispatcher app | rebuilt with `./run.sh --mobile` at each new network | **test builds only**: Sign in > Server, type the laptop's address (e.g. `10.0.52.117`). It checks the server answers, or offers "Save anyway". A released app ignores this and uses its fixed server |
| Edge (camera) app | already had a server field in Set-up | unchanged |

- `./run.sh` prints the address to type on the phones. When the network
  changes, nothing on the laptop needs restarting.
- `SABAYGO_BACKEND_PORT`, used when another program holds port 8000,
  now reaches the console too. The run summary shows the port to type.
- A tester who is already signed in signs out to change the server.
  Signing out keeps a Dispatcher's unsent records.

**After you pull:** run `./run.sh` once (the console rebuilds one last
time) and `./run.sh --mobile` once to put the new app on your test
phone.

## 3. Deployment design

`docs/DEPLOYMENT.md`:
- **One cloud server** at a fixed `https://` address. The Terminal
  Manager and Cashier use the console in a browser, and the Dispatcher,
  passengers and camera phone use the internet.
- **The camera phone in the van** sends its counts over its own mobile
  data. The Tapo talks only to that phone's hotspot. It *can* reach the
  internet through the hotspot, so its TP-Link account must be the
  cooperative's and cloud recording stays off.
- **Rules the server must keep:** one backend process, MySQL on Manila
  time, migrations through `db/apply.sh`, no dev accounts, nightly
  backups.

Decisions needed (the owner's, with the team):
1. Hosting: a paid server in Singapore, or a free tier.
2. Domain: a bought name or a free subdomain.
3. SOS text messages: the SMS gateway app's cloud relay, Twilio, or off.
4. Data: A2Z's agreement to store passenger data and door photos on a
   cloud server (Data Privacy Act of 2012).
5. Getting the app onto phones: an APK download link, or Play Store
   internal testing.

## 4. Phones over their USB cable (21 Nov work, committed now)

`usb_phones.sh` opens a USB tunnel for each plugged-in phone and
installs the app. `--watch` reopens a tunnel within 3 s after a cable
reset. It is for networks that keep devices apart, like the school's
LIC-WIFI-OPEN, and it is how today's camera test reached the laptop.
